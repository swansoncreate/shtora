# План реализации сквозной диагностики Shtora

Основная спецификация: [observability-tracing.md](./observability-tracing.md).  
Схема событий: [observability-event-schema.md](./observability-event-schema.md).

## Рабочие правила

- Реализация начинается с карты фактического кода, а не с предположений об именах функций.
- Не менять `main` функциональным кодом в рамках этапа проектирования; этот файл-план описывает будущую реализацию.
- Существующие PR по диагностике сначала сравнить и свести в одну линию изменений.
- VPS и пользовательские данные не трогать до успешного CI и отдельного разрешения на развёртывание.
- Любое событие, значение или метрика, которую нельзя достоверно получить, помечать как недоступную, не подставлять догадку.

## Этап A — аудит и карта потоков

- [ ] Найти все UI entry points ленты, чата, Imagine и просмотра/изменения изображения.
- [ ] Найти генераторы промптов, нормализаторы payload и точки вызова Imagine/Grok.
- [ ] Найти все сериализации/десериализации JSON и HTTP boundaries.
- [ ] Найти места записи изображений, постов, сообщений и обновления состояния.
- [ ] Для каждого участка зафиксировать файл, функцию, runtime (browser/VPS/Grok Build), JSON input/output и известные ограничения наблюдаемости.
- [ ] Нарисовать sequence diagram для feed и chat отдельно.
- [ ] Проверить, какие участки Grok Build доступны для изменения, а какие остаются внешней границей.

**Выход:** карта вызовов и таблица JSON-контрактов с точными ссылками на исходники.

## Этап B — схема и ядро

- [ ] Типы событий и версия схемы.
- [ ] Генерация traceId/operationId/spanId/parentSpanId.
- [ ] Проброс trace context через browser → API → server → upstream, где это поддерживается.
- [ ] Async context на сервере либо явная передача контекста.
- [ ] Safe JSON inspector с классификацией полей, ограничением глубины и размера.
- [ ] Redaction allowlist для headers, URL, prompt и ошибок.
- [ ] JSONL writer с очередью, backpressure/лимитом очереди, ротацией, правами и безопасным отказом.
- [ ] Флаг подробной диагностики с явным сроком действия.
- [ ] Тесты на параллельные trace, перепутывание parent spans, отказ диска, ротацию и инъекцию строк.

**Выход:** отдельный проверенный диагностический модуль без изменения бизнес-логики.

## Этап C — транспорт и JSON

- [ ] Инструментировать реальный HTTP client/fetch в месте фактического вызова.
- [ ] Записывать method, destination без секретов, allowlisted headers, request/response bytes и статус.
- [ ] Разделять время до response headers, чтение тела, JSON parse и validation.
- [ ] Зафиксировать фактическую JSON-структуру на входе и выходе с типами, длинами, количеством полей и хешем.
- [ ] Записать parse error/validation error без небезопасного дампа полного body.
- [ ] Добавить тест, доказывающий совпадение prompt.final с prompt в фактическом теле запроса.

**Выход:** можно точно ответить, что Shtora отправила и что получила на контролируемой сетевой границе.

## Этап D — лента

- [ ] Trace от действия пользователя/планировщика до завершения операции.
- [ ] Измерять загрузку контекста, выбор персонажа/настроек и сборку промпта.
- [ ] Записывать prompt draft/final по политике безопасности.
- [ ] Фиксировать параметры Imagine и количество image references.
- [ ] Измерять upstream request/response и обработку результата.
- [ ] Фиксировать создание объекта поста, запись и выдачу через API.
- [ ] Добавить клиентское подтверждение появления результата, если сервер не может доказать видимость.
- [ ] Покрыть успешный сценарий и отказы на каждом этапе тестами.

**Выход:** по trace ID можно определить, почему генерация не создала пост или почему пост не появился в UI.

## Этап E — чат

- [ ] Trace от отправки сообщения до обновлённого диалога.
- [ ] Измерять загрузку контекста и разрешение intent.
- [ ] Отдельно отслеживать обычный текстовый ответ, генерацию нового изображения, редактирование существующего и POV/новую сцену.
- [ ] Сравнивать промпты до/после модификации и фактический payload.
- [ ] Фиксировать ответ модели, parse/schema, выбор результата и связь с исходным медиа.
- [ ] Измерять сохранение сообщения/изображения и обновление thread.
- [ ] Проверить отсутствие дублей, потерянных изображений и неправильного parent span при параллельных запросах.

**Выход:** по trace ID можно найти место, где запрос фото не распознался, генерация не состоялась или результат не сохранился/не отобразился.

## Этап F — VPS, браузер и внешний Grok Build

- [ ] Коррелировать browser/server события безопасным trace ID.
- [ ] Добавить client-side fetch timings, abort, offline/online и unhandled errors.
- [ ] Добавить host samples: CPU/load, memory, disk, uptime, restart count и health.
- [ ] Измерять доступные DNS/connect/TLS/TTFB показатели с VPS.
- [ ] Ограничить доступ к логам и проверить ротацию.
- [ ] Инструментировать Grok Build только если исходный код и среда это позволяют.
- [ ] В противном случае оформить внешний boundary с request/response на стороне Shtora и явно указать, что внутренний trace Grok недоступен.

**Выход:** видны клиентские, серверные и host-метрики; внешняя граница не маскируется под полную трассировку.

## Этап G — обзор, экспорт и метрики

- [ ] Фильтр по traceId, operation, scenario, статусу, времени и типу ошибки.
- [ ] Временная шкала со вложенными spans и file/function/line.
- [ ] Просмотр JSON-структуры: вход/выход, поля, типы, размеры, различия и hash.
- [ ] Показ prompt draft/final/actual payload только в защищённом режиме.
- [ ] Экспорт JSONL с предварительным просмотром и редактированием.
- [ ] Агрегаты p50/p90/p95/p99, error rate, timeout rate, retry count и объём JSON.
- [ ] Не использовать пользовательские значения как metric labels.
- [ ] Документировать retention, права и процедуру удаления логов.

## Этап H — качество и выпуск

- [ ] Typecheck, lint, build и полный test suite.
- [ ] Unit tests для redaction, safe JSON, trace propagation и ротации.
- [ ] Integration tests для feed/chat pipeline и контролируемого upstream.
- [ ] Проверить HTTP 4xx/5xx, timeout, network reset, empty body, malformed JSON, invalid schema и storage failure.
- [ ] Проверить, что журнал не ломает операции при отказе файловой системы.
- [ ] Проверить, что секреты не попадают в события, клиентский экспорт и CI artifacts.
- [ ] Повторно проверить ранее упавший CI test `socket closed` и установить, flaky он или регрессия.
- [ ] Проверить полный trace на успешном и неуспешном сценарии.
- [ ] Отдельно согласовать deployment/rollback; не выполнять deploy автоматически.

## Определение готовности

Реализация считается готовой только когда feed и chat имеют end-to-end trace с реальными file/function/line, JSON boundaries, фактическим prompt/payload, сетевыми метриками, сохранением и тестами приватности. Наличие только VPS ping, health-check или общего события `request failed` критериям не соответствует.
