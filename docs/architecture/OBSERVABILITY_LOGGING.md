# Shtora — ТЗ: сквозное диагностическое логирование

**Статус:** Draft for Architecture Review  
**Приоритет:** Высокий  
**Тип задачи:** Сквозная наблюдаемость и диагностика существующего приложения  
**Область:** Клиент, сервер, чат, лента Instagram, Dropbox, Imagine, генерация и обработка медиа, хранение данных, интеграции и фоновые задачи.

## 1. Цель

Сделать работу Shtora максимально прозрачной для диагностики: по логам разработчик должен восстановить, **что пользователь сделал, какие внутренние шаги выполнились, какие данные и промпты приложение сформировало и куда отправило, что получило в ответ, как обработало результат и где возникла проблема**.

Логирование должно помогать разбирать как явные ошибки, так и тихие дефекты: повторяющиеся фотографии, неверный выбор Dropbox-источника, неожиданный промпт, потерю контекста персонажа, отсутствие ответа чата, зависшую генерацию, рассинхронизацию интерфейса и сервера, проблемы сохранения и повторные запросы.

Это ТЗ описывает отдельный слой наблюдаемости поверх существующей архитектуры. **Не переписывать приложение, не менять поведение функций ради логирования и не удалять существующие возможности.** Инструментирование должно внедряться постепенно и сохранять совместимость с текущими способами запуска, Grok-публикацией и VPS.

## 2. Главный принцип: одна сквозная история операции

Каждое значимое действие должно иметь единый `trace_id` и, при необходимости, `parent_span_id`. По одному ID можно найти связанные записи клиента, API, чата, выбора источника, генерации, файловой системы и сохранения результата.

Пример цепочки:

```text
Пользователь нажал «Сгенерировать»
  → UI event
  → API request
  → auth/session check (без записи секретов)
  → chat / Imagine intent
  → context loaded
  → prompt compiled
  → source/reference selected
  → provider request initiated
  → provider response received
  → response parsed
  → image saved
  → database/state updated
  → API response
  → UI rendered result
```

Каждый этап обязан завершиться явным событием `success`, `failure`, `skipped` или `cancelled`. Если этап не был запущен, где это важно для диагностики, записывать причину пропуска. Не создавать фиктивные записи о действиях, которых приложение фактически не выполняло.

## 3. Что логировать

### 3.1 Общие поля каждой записи

Все записи — структурированные JSON-объекты, а не только произвольные строки. Базовая схема:

- `timestamp` — UTC, ISO 8601 с миллисекундами;
- `level` — `trace`, `debug`, `info`, `warn`, `error`, `fatal`;
- `event` — стабильное машинное имя события, например `imagine.prompt.compiled`;
- `message` — короткое человекочитаемое пояснение;
- `trace_id`, `span_id`, `parent_span_id` — сквозная трассировка;
- `request_id`, `job_id`, `conversation_id`, `message_id`, `media_id`, `scene_id` — где применимо;
- `session_id_hash` — только необратимый/псевдонимизированный идентификатор сессии, никогда не cookie;
- `component`, `operation`, `route`, `method`;
- `duration_ms`, `status`, `attempt`, `retry_count`;
- `app_version`, `git_sha`, `environment`, `host_instance`;
- `provider`, `model`, `provider_request_id` — когда известны;
- `error.name`, `error.code`, `error.message`, `error.stack`, `error.cause` — при ошибке с редактированием секретов.

Поля должны быть согласованы между клиентом и сервером. Значения, которых нет, опускать, а не выдумывать. Не записывать токены авторизации, пароли, cookie, RPC-ключи и другие секреты даже в debug/trace.

### 3.2 UI и пользовательские действия

Логировать значимые действия интерфейса, чтобы понять, какое действие вызвало цепочку:

- открытие разделов Feed/Instagram, личного чата, Dropbox, Imagine, Settings;
- открытие поста и просмотрщика фотографии;
- нажатия «сохранить», «изменить через Imagine», отправка сообщения, отправка/повтор генерации;
- выбранные параметры Imagine, источник изображения и режим редактирования;
- начало/окончание загрузки, ожидание, отмена, повтор, показ ошибки;
- запросы, которые были отменены или заменены более новыми;
- ошибки клиентского рендеринга и необработанные исключения.

Для события фиксировать имя действия, безопасные параметры, текущий экран и correlation ID. Не логировать каждый ввод символа в поле, движения курсора или другие шумные события. Для текстовых полей — логировать отправленное значение только в соответствии с правилами содержимого ниже.

### 3.3 HTTP, API и сервер

Для каждого входящего API-запроса логировать начало и завершение:

- метод, нормализованный путь, статус, длительность;
- размер запроса/ответа, если доступен;
- идентификатор запроса и трассировки;
- результат проверки сессии/авторизации: только решение и тип механизма, не credential;
- ошибки разбора/валидации с названием поля и причиной;
- тайм-ауты, отмены клиентом, ограничения частоты, ретраи;
- внутренние вызовы и их результаты;
- ошибки чтения/записи файлов, БД и сетевых операций.

Не писать значения query-параметров и заголовков целиком: в URL и заголовках могут оказаться секреты. Для логирования использовать allowlist безопасных полей и redact denylist.

### 3.4 Чат и персонаж

Для каждого сообщения и каждого шага обработки фиксировать:

- факт получения пользовательского сообщения, его `message_id`, длину и при разрешённом content logging — полный текст;
- идентификатор разговора, историю/контекст, реально выбранные для запроса сообщения и правила усечения;
- какие persona, relationship/world state, память и настройки были загружены;
- какие контекстные блоки включены или исключены и почему;
- сформированный system/developer/user prompt и фактический payload, подготовленный к отправке;
- куда отправлен запрос: адаптер/маршрут/провайдер, endpoint-категория, модель/режим, параметры генерации;
- начало/конец вызова, длительность, число попыток, тайм-аут, статус;
- фактически полученный ответ провайдера, сырой ответ там, где он доступен, и распарсенный результат;
- постобработку ответа: какие поля извлечены, изменены, отброшены или не прошли валидацию;
- сохранённый ответ, итоговый статус сообщения и то, что сервер отдал клиенту;
- классификацию намерения, решение о генерации медиа, выбор инструментов/действий и причину каждого решения;
- ошибки, fallback-ветки, отсутствие ответа и причину.

Различать **исходный текст провайдера**, **результат парсинга**, **постобработанный текст** и **фактически отображённый/сохранённый ответ**. Не подменять один другим в логах.

### 3.5 Лента Instagram и фото

Логировать:

- запрос на построение/обновление ленты;
- алгоритм и параметры выборки, выбранные посты и причины включения/исключения;
- ID поста, ID медиа, путь/идентификатор исходного изображения, источник и время;
- все этапы выбора фотографии, фильтры, результаты кандидатов и причину выбора победившего кандидата;
- историю недавно использованных источников, правила anti-repeat и причины повторного использования;
- создание/обновление/удаление поста и изменение метаданных;
- открытие просмотрщика, сохранение файла, экспорт, запуск Imagine из просмотрщика;
- ошибки загрузки изображения, HTTP-код, MIME, размер и безопасный путь/ID ресурса.

Для диагностики повторов должно быть возможно увидеть, почему одна и та же фотография была выбрана снова: список рассмотренных кандидатов, исключения и точную причину выбора. Не записывать бинарное содержимое изображений в текстовый лог.

### 3.6 Dropbox

Логировать полный жизненный цикл работы с хранилищем:

- пользовательское действие и исходный запрос;
- операцию: список, поиск, просмотр, импорт, экспорт, сохранение, удаление, переименование;
- корневой источник и безопасный относительный путь/ID;
- количество найденных кандидатов и причины фильтрации;
- выбранный файл, MIME, размер, контрольную сумму при необходимости;
- сопоставление с персонажем/постом/Imagine job;
- фактический результат операции и ошибки;
- причины, почему ожидаемый файл не найден или был выбран другой.

Не логировать содержимое бинарных файлов, секретные абсолютные пути с credential-компонентами или данные окружения.

### 3.7 Imagine и обработка изображений

Для каждого Imagine job нужен полный аудит жизненного цикла:

`created → queued → planning → prompt_compiled → source_selected → provider_started → provider_responded → result_parsed → persisted → completed`

Возможные альтернативные финальные состояния: `failed`, `cancelled`, `timed_out`, `rejected`, `partial`.

Записывать:

- инициирующее действие и исходный media ID;
- цель: генерация с нуля, редактирование, продолжение сцены, смена позы/одежды, POV и т.п.;
- PhotoIntent/ScenePlan/WorldSnapshot и их версии;
- входные изображения: ID/относительный путь, роль каждого reference, порядок и контрольная сумма, если доступна;
- исходный prompt, собранные фрагменты, итоговый prompt, negative prompt и параметры;
- все трансформации prompt, их причины и компонент, выполнивший изменение;
- реальный payload, отправленный адаптеру провайдера, включая доступные параметры;
- провайдера, модель/режим, request ID, длительность, попытки, лимиты и стоимость/usage, если провайдер их сообщает;
- сырой доступный ответ провайдера, URL/ID результата, метаданные и ошибки;
- постобработку, путь/ID сохранённого результата и связанный media ID;
- причину выбора fallback или повторной генерации;
- связь между оригиналом и производными изображениями: `parent_media_id`, `job_id`, `scene_id`.

Не считать job завершённым только потому, что провайдер вернул ответ: отдельно подтвердить, что результат скачан/получен, сохранён и связан с записью приложения.

### 3.8 Файлы, база данных и фоновые задачи

Логировать значимые чтения/записи и изменения состояния: имя операции, сущность/ID, результат, длительность, число изменённых записей и безопасный diff полей. Не писать целиком БД, все строки таблиц или секретные значения при каждом запросе.

Для очередей и фоновых задач записывать создание, запуск, heartbeat/прогресс для долгих работ, retry, задержку, завершение, отмену, dead-letter/постоянный отказ и связь с исходным действием.

Для важных изменений состояния использовать события аудита, позволяющие восстановить порядок изменений, не превращая обычные логи в копию всей базы.

### 3.9 Инфраструктура и диагностика запуска

Записывать:

- старт и остановку приложения, версию/commit, время запуска и режим;
- состояние ключевых подсистем и доступность зависимостей;
- uncaught exceptions, unhandled rejections, ошибки фоновых задач;
- нехватку места, ошибки файловой системы, недоступность сети/провайдера, тайм-ауты;
- рестарты, graceful shutdown, завершение процесса и health-check;
- частоту ошибок и медленные операции.

Не записывать все переменные окружения. Разрешено логировать только allowlist безопасных конфигурационных флагов; секреты не должны попадать в логи даже при диагностике старта.

## 4. Содержимое промптов и ответов: два уровня логирования

Поскольку цель — видеть точные промпты и ответы, предусмотреть два независимых уровня:

1. **Operational log** — всегда включён: метаданные, ID, длительность, статусы, размеры, хеши, ошибки, версия prompt template и редактированные диагностические сведения.
2. **Content trace** — защищённый режим для полного содержимого промптов, сообщений, контекста и ответов. Должен поддерживать явное включение для диагностики и быть настраиваемым по окружению/периоду. Когда включён, сохранять точные данные, фактически подготовленные к отправке и полученные от провайдера, в раздельном защищённом хранилище.

Content trace — это не обычный публичный application log. Доступ к нему должен быть ограничен администратором сервера; UI не должен отдавать эти записи обычному пользователю или клиентскому JavaScript. В production режим содержимого должен быть явно сконфигурирован и видим в диагностическом статусе, чтобы было понятно, почему полные промпты не попали в журнал.

Для каждой записи content trace сохранять метаданные и ссылку на соответствующий operational event. Если платформа/провайдер скрывает внутренний prompt, chain-of-thought, скрытые системные инструкции или сырые сетевые данные, приложение не может достоверно записать то, к чему у него нет доступа. В этом случае логировать фактический payload на границе приложения, доступный ответ, request ID и явно отмечать границу наблюдаемости. Не заявлять, что записан внутренний ход рассуждений провайдера.

## 5. Секреты и приватность — обязательные ограничения

Полнота логов не означает запись секретов. На любом уровне, включая trace/debug, обязательно редактировать:

- пароли, коды входа, cookies, session tokens;
- `Authorization`, API keys, RPC keys, подписи и секреты сессий;
- значения переменных окружения, если они не внесены в allowlist безопасных флагов;
- приватные URL с подписанными query-параметрами;
- любые другие credential-подобные значения.

Полные сообщения, контекст персонажа и промпты могут содержать личный или чувствительный контент. Требования:

- хранить content trace отдельно от общих технических логов;
- ограничить доступ на уровне ОС/сервера и не раздавать через публичные статические директории или обычные API;
- задавать сроки хранения и автоматическую очистку;
- предусмотреть удаление/экспорт trace по ID и удаление связанных данных в рамках правил приложения;
- не отправлять диагностические логи в сторонний сервис по умолчанию;
- логировать включение/выключение content trace и доступ к нему;
- не помещать полные prompt/response в системный журнал, если его доступ и срок хранения не контролируются приложением.

По умолчанию содержимое должно быть выключено или маскировано до явного включения, но метаданные сквозной диагностики — включены. Это не должно мешать включить полный trace для воспроизведения конкретной ошибки.

## 6. Архитектура хранения и формат

- Использовать единый логгер с типизированными event names и общими полями, а не разрозненные `console.log` с несовместимыми форматами.
- Выводить operational logs в структурированном JSON Lines (одна запись на строку).
- Хранить локально на VPS вне каталога публичной статики и вне пользовательского `data`-каталога; права доступа — минимально необходимые.
- Разделять обычные логи и content trace по файлам/хранилищам, правам и срокам хранения.
- Реализовать ротацию по размеру/времени, сжатие архивов и ограничение общего объёма; защита от бесконечного роста обязательна.
- Ошибка записи логов не должна ломать чат, ленту, Dropbox или Imagine. При невозможности записи — аварийный безопасный fallback и счётчик потери логов.
- Не логировать целиком HTTP request/response middleware автоматически без редактирования. Все поля должны проходить единый redaction layer.
- При необходимости поддержать экспорт диагностического пакета по `trace_id`/времени с маскированием секретов и манифестом файлов.

Формат и backend хранения выбрать с учётом реальной среды Shtora. На первом этапе не добавлять внешнюю платную observability-платформу и не делать её обязательной зависимостью.

## 7. Поиск и чтение логов

Нужна практическая процедура, чтобы разработчик мог получить полную историю проблемы:

- поиск по `trace_id`, `request_id`, `job_id`, `conversation_id`, `message_id`, `media_id` и временному интервалу;
- группировка событий в хронологическую цепочку;
- просмотр prompt/response content trace при наличии прав и включённого режима;
- фильтры по компоненту, уровню, событию, статусу, провайдеру и длительности;
- понятная ошибка, если trace не существует, уже очищен или content logging был выключен;
- диагностический пакет, который можно безопасно передать на анализ без ключей и паролей.

На первом этапе допустимы JSONL-файлы и команды/скрипт поиска по ID, если отдельный UI логов непропорционально усложнит проект. Важнее полнота и сквозная связность данных, чем отдельная панель.

## 8. Производительность и отказоустойчивость

- Не блокировать критический пользовательский путь медленной записью в файл/сеть.
- Использовать буферизованную/асинхронную запись с ограниченным буфером и backpressure.
- Измерять потерянные записи, переполнение очереди логгера и задержку записи.
- Ограничивать объём одной записи и безопасно обрабатывать большие ответы/промпты; содержимое сохранять отдельно, в логах — ссылка и checksum.
- Не включать высокочастотные trace-события постоянно без ограничений.
- При ошибке логгера основная операция должна продолжаться, кроме тех случаев, когда запись обязательного audit-события является требованием безопасности.
- Ретраи логирования не должны бесконечно блокировать процесс.

## 9. Пошаговое внедрение

### Этап 1 — фундамент

- единый структурированный logger;
- correlation/trace IDs и propagation между клиентом, сервером, API и job;
- redaction секретов;
- обработчики ошибок, старта/остановки;
- ротация, права доступа, ограничение диска;
- документированная конфигурация и тесты.

### Этап 2 — чат и провайдеры

- логирование фактических prompt payload, доступных ответов, parsing/post-processing и ошибок;
- Content trace с отдельными правами и настройкой;
- request/job IDs и метрики длительности, retry, timeout.

### Этап 3 — Feed, Dropbox и Imagine

- трассировка выбора постов и исходных фото;
- anti-repeat: кандидаты, исключения, причины выбора;
- полный Imagine lifecycle и связи reference/original/result;
- события сохранения файлов и обновления состояния.

### Этап 4 — пользовательские сценарии и диагностика

- UI events для основных действий;
- инструмент поиска/сборки trace по ID;
- диагностический экспорт;
- проверка реальными сценариями и документация runbook.

Этапы внедрять инкрементально. Не выполнять массовую замену существующих модулей одним большим коммитом.

## 10. Конфигурация

Предусмотреть документированные настройки, например:

- `SHTORA_LOG_LEVEL` — уровень operational log;
- `SHTORA_LOG_DIR` — каталог логов вне public и user data;
- `SHTORA_LOG_MAX_SIZE` / `SHTORA_LOG_RETENTION_DAYS` — ротация и хранение;
- `SHTORA_CONTENT_TRACE_ENABLED` — явное включение полного содержимого;
- `SHTORA_CONTENT_TRACE_RETENTION_DAYS` — срок хранения content trace;
- `SHTORA_LOG_REDACT` — обязательная редактирующая обработка, которую нельзя отключить в production.

Это предлагаемые имена конфигурации; перед реализацией проверить существующие настройки и переиспользовать совместимые, не создавать дублирующие переменные без необходимости. Секреты никогда не должны управляться через клиентские переменные `VITE_*`.

## 11. Приёмочные критерии

1. По одному `trace_id` можно восстановить действие пользователя и все связанные серверные операции в правильном порядке.
2. Для сообщения чата видны исходный текст (в content trace, когда включён), собранный контекст, точный payload на границе провайдера, доступный ответ, результат parsing/post-processing и сохранённый/отображённый текст.
3. Для Imagine видны инициирующее действие, intent, все prompt-этапы, ссылки на исходные изображения, провайдер, попытки, ответ и подтверждение сохранения результата.
4. Для Feed видны кандидаты изображений, фильтры, причины выбора и объяснение повторного использования фотографии.
5. Для Dropbox видны запрос, выбранный путь/ID, фильтрация, результат и ошибки.
6. Ошибка на любом этапе содержит event name, trace/job ID, длительность и полезную причину, а не только «что-то пошло не так».
7. Можно отличить тайм-аут провайдера, ошибку парсинга, ошибку скачивания, ошибку записи и ошибку UI.
8. Полные prompt/response доступны только в явно включённом защищённом режиме; обычные логи остаются полезными при выключенном content trace.
9. Секреты не появляются в тестовых логах даже при намеренно подставленных тестовых токенах, cookie, паролях и ключах.
10. Ротация и очистка работают; логи не заполняют диск и не хранятся в публичной директории.
11. Если логгер недоступен, обычные операции приложения продолжаются, а потеря диагностических записей учитывается.
12. Логирование не меняет бизнес-логику, ответы, порядок операций и поведение Grok/VPS.
13. Автотестами покрыты trace propagation, redaction, ошибки/ретраи и ротация.
14. Документация объясняет, где лежат operational logs и content trace, как найти trace по ID, как безопасно собрать диагностический пакет и как включать/выключать полный trace.

## 12. Ограничения и важные оговорки

- Логировать только то, что приложение реально наблюдает. Если внешняя платформа скрывает внутренние запросы, внутренние инструменты или ответные данные, которые не возвращаются приложению, это помечается как граница наблюдаемости.
- Не пытаться обходить ограничения платформы или перехватывать чужие сессии. Диагностировать собственные запросы и ответы на контролируемой границе приложения.
- Не менять текущую схему хранения пользовательских данных ради логирования без отдельного плана миграции и резервного копирования.
- Не удалять и не очищать существующие пользовательские данные; не хранить логи внутри `/opt/shtora/data` без отдельного обоснования и проверки свободного места.
- Перед установкой на VPS проверить фактическую структуру деплоя, текущий systemd unit и права каталогов. Любые изменения VPS — отдельный контролируемый шаг с резервной копией и проверкой отката.

## 13. Что не входит в это ТЗ

- Переписывание чата, ленты, Dropbox или Imagine.
- Изменение промптов/моделей или бизнес-логики генерации.
- Обязательная покупка внешнего сервиса логирования.
- Логирование секретов, паролей, токенов или недоступных приложению внутренних рассуждений модели.
- Удаление, миграция или переформатирование пользовательских файлов и БД.

**Итог:** после внедрения разработчик должен иметь возможность пройти от действия пользователя до фактического результата по единой трассе, видеть точные доступные приложению prompt/response payloads и понимать, на каком этапе, почему и с какими данными возникла проблема.
